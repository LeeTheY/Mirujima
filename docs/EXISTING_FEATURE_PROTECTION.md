# 기존 기능 보호 및 회귀 방지 명세

> 이 문서는 미루지마에 새로운 기능을 추가할 때 현재 정상 동작하는 기능을 보호하기 위한 공통 규칙이다.
> 기능 구현 시 `AGENTS.md`, 해당 추가 기능 문서와 함께 읽고 적용한다.
>
> 문서 버전: `1.0`
> 작성 기준일: `2026-07-15`

---

## 1. 핵심 원칙

현재 구현되어 정상 동작하는 모든 기능은 확정된 기존 동작으로 간주한다.

- 기존 기능의 사용자 동작, 상태 전환, 계산 결과, 저장 형식, 알림 정책, 차단 정책을 변경하지 않는다.
- 새로운 기능은 기존 기능 위에 추가하는 `additive change` 방식으로 구현한다.
- 요청과 무관한 리팩터링, 파일명 변경, 함수명 변경, 타입 재설계, 폴더 재구성을 하지 않는다.
- 코드를 정리하거나 더 깔끔하게 만들기 위한 목적만으로 기존 로직을 수정하지 않는다.
- 기존 테스트를 삭제하거나 기대값을 변경하여 통과시키지 않는다.
- 기존 오류를 발견하더라도 이번 요청 범위가 아니면 임의로 수정하지 않고 최종 보고에 기록한다.
- 기존 동작 변경이 불가피하면 구현을 멈추고 이유, 영향 범위, 대안을 먼저 사용자에게 보고한다.

---

## 2. 동결되는 기존 동작

별도의 변경 승인이 없는 한 다음 영역의 동작 계약을 동결한다.

- 일정 생성·수정·삭제
- 일정 시간과 목표 집중 시간 계산
- 집중 시작·일시정지·재개·종료
- 완료·미완료 결과 선택과 확인
- 누적 휴식 시간과 휴식 종료 알림
- Allowlist·Blocklist·Off 차단 정책
- DNR 규칙 생성·적용·제거·복구
- 임시 허용과 만료
- 자리 비움과 FocusHealth 판정
- 알림 중복 방지와 테스트 알림 예외
- Popup에서 Side Panel 열기
- 배지와 미처리 알림
- 일일 리포트 계산과 생성
- 현재 storage key의 의미와 migration
- 개인정보 수집 범위
- Chrome·Service Worker 재시작 복구
- Popup 380px, Side Panel, 전체 확장 페이지의 확정 UI 규격

새 기능 문서가 위 동작 중 하나의 변경을 명시적으로 요구한다면 자동으로 변경하지 않는다. 충돌 내용과 선택 가능한 대안을 먼저 보고하고 사용자 승인을 받는다.

## 3. 허용되는 변경

새 기능을 연결하기 위해 다음 변경은 허용한다.

- 기존 화면에 새로운 컴포넌트, 카드 또는 버튼 추가
- 기존 레이아웃 규격 안에서 영역 위치 조정
- 기존 함수 호출 전후에 새로운 기능을 연결하는 hook 또는 adapter 추가
- 새로운 메시지 타입, repository, service, storage key 추가
- 기존 타입을 깨뜨리지 않는 optional field 추가
- 기존 모듈을 새 기능에서 사용하기 위한 re-export
- 기존 동작을 유지하는 최소한의 import 변경
- 새 기능 실패를 격리하기 위한 독립적인 오류 처리 추가
- 새 기능 전용 migration과 기본값 추가

레이아웃이나 파일 위치를 조정하더라도 기존 버튼의 의미, 이벤트 처리, 상태 전환과 결과는 동일해야 한다.

---

## 4. 금지되는 변경

- 기존 함수 내부 조건문과 계산식 변경
- 기존 상태 머신 전환 변경
- 기존 일정·집중·휴식·차단·알림·리포트 로직 변경
- 기존 storage key의 의미 또는 데이터 형식 변경
- migration 없이 기존 저장 데이터를 새 형식으로 덮어쓰기
- 기존 메시지의 payload 또는 응답 의미 변경
- 기존 컴포넌트의 이벤트를 새 이벤트로 교체
- 기존 예외 처리 제거 또는 완화
- 기존 개인정보 수집 범위 확대
- 기존 기능을 새로운 서버, 로그인 또는 결제에 종속시키기
- 새 기능이 실패하면 기존 기능도 실패하도록 연결
- 기존 테스트 삭제, skip 처리 또는 기대값 완화
- 타입 오류를 `any`, 무분별한 assertion, non-null assertion으로 숨기기
- 요청과 무관한 코드 정리와 대규모 리팩터링

## 5. 기존 파일을 수정해야 할 때

기존 파일 수정은 새 기능 진입점을 연결하는 최소 범위에서만 허용한다.

허용 예시:

- `FOCUS_START` 성공 후 탭 정리 기능을 독립적으로 호출
- Settings에 멤버십 카드 추가
- 공용 `ExtensionMessage` union에 새 메시지 추가
- MainShell에 새 페이지 진입점 추가
- 기존 repository interface를 깨뜨리지 않는 adapter 추가

수정 전 다음을 확인한다.

1. 새 파일이나 adapter만으로 구현할 수 없는가
2. 기존 로직을 수정하지 않고 호출만 추가할 수 있는가
3. 새 기능을 feature flag 또는 설정으로 격리할 수 있는가
4. 새 기능이 실패해도 기존 기능이 계속 동작하는가
5. 기존 사용자의 데이터와 기본 설정이 유지되는가
6. 기존 테스트 기대값을 변경하지 않고 구현할 수 있는가

기존 파일을 수정한 경우 최종 보고에 파일, 수정 이유, 기존 동작 보존 방법을 명시한다.

## 6. Additive Change 구현 규칙

새 기능은 가능한 한 다음 구조를 사용한다.

```text
기존 기능
→ 기존 결과 확정
→ 새 기능 hook 또는 adapter 호출
→ 새 기능 성공·실패를 독립적으로 처리
```

피해야 할 구조:

```text
기존 기능
→ 새 기능 성공 여부에 종속
→ 새 기능 실패 시 기존 기능도 중단
```

예를 들어 탭 자동 그룹화가 실패해도 집중 세션과 DNR 차단은 정상적으로 시작되어야 한다. 클라우드 동기화가 실패해도 Free 로컬 일정과 집중 기능은 계속 사용할 수 있어야 한다.

---

## 7. 저장소와 데이터 보호

- 기존 storage schema version을 먼저 확인한다.
- 새 데이터는 새 key 또는 하위 호환 optional field로 추가한다.
- schema version 변경 시 migration을 작성한다.
- migration은 idempotent해야 한다.
- migration 실패 시 기존 데이터를 삭제하지 않는다.
- 새 기능을 사용하지 않는 기존 사용자의 데이터 구조와 동작을 보존한다.
- 기본값은 기존 사용자 경험을 갑자기 바꾸지 않는 방향으로 선택한다.
- 서버 동기화 기능을 추가하더라도 로컬 원본을 안전하게 백업한 뒤 이동한다.

---

## 8. 오류 격리

- 새 기능의 작업 오류는 기존 앱 전체 fatal error로 전파하지 않는다.
- 새 기능 실패는 해당 기능 영역의 banner 또는 결과 메시지로 표시한다.
- 기존 일정·집중·차단 요청의 성공 결과를 새 기능 실패 때문에 실패로 바꾸지 않는다.
- 일부 항목 실패 시 가능한 항목은 계속 처리한다.
- 재시도는 idempotent하게 구현하고 중복 데이터·그룹·알림을 만들지 않는다.
- 외부 서비스 오류가 발생해도 로컬 핵심 기능은 계속 사용할 수 있어야 한다.

## 9. 테스트 기준

### 9.1 구현 전

- 현재 typecheck, lint, test, build 결과를 기준선으로 기록한다.
- 현재 테스트 파일과 테스트 개수를 확인한다.
- 변경 대상 기존 기능의 테스트가 부족하면 동작을 고정하는 characterization test를 먼저 추가한다.

### 9.2 구현 중

- 기존 테스트는 유지한다.
- 기존 테스트의 기대값을 새 기능에 맞춰 임의로 변경하지 않는다.
- 새 기능 테스트를 별도로 추가한다.
- 새 기능 실패가 기존 기능을 중단하지 않는 통합 테스트를 추가한다.
- migration과 Service Worker 재시작 복구를 테스트한다.

### 9.3 구현 후

최소 다음을 실행한다.

```bash
npm run typecheck
npm run lint
npm test
npm run build
```

기존 `AGENTS.md`의 Chrome 수동 회귀 항목과 새 기능 문서의 수동 검증 항목을 함께 확인한다.

## 10. 불가피한 기존 동작 변경

기존 동작 변경이 불가피하면 임의로 구현하지 않는다.

먼저 다음 형식으로 보고한다.

```text
변경이 필요한 기존 동작:
변경이 필요한 이유:
영향받는 사용자 흐름:
영향받는 storage·message·permission:
변경하지 않는 대안:
추천안:
필요한 migration과 회귀 테스트:
```

사용자의 명시적 승인 전에는 해당 기존 로직을 변경하지 않는다.

기존 기능의 동작이 승인 없이 달라졌다면 완료로 처리하지 않는다.

## 12. 기능 구현 요청 예시

### 12.1 스마트 탭 그룹화

```text
AGENTS.md를 기본 프로젝트 명세로 읽고,
docs/EXISTING_FEATURE_PROTECTION.md를 기존 기능 보호 규칙으로 읽고,
docs/SMART_TAB_GROUPING.md를 추가 기능 명세로 읽어 구현해줘.

현재 개발된 기능의 동작 계약은 동결된 것으로 간주하고,
새 기능은 additive change 방식으로 구현해줘.

UI 배치, import, adapter, hook 추가처럼 연결에 필요한 최소 변경은 허용하지만,
기존 일정·집중·휴식·차단·알림·리포트 로직과 저장 데이터의 의미는 변경하지 마.

기존 동작 변경이 불가피하면 임의로 진행하지 말고 이유와 대안을 먼저 보고해줘.

기존 테스트를 삭제하거나 기대값을 변경하지 말고,
신규 테스트와 회귀 테스트를 추가한 뒤
typecheck, lint, test, build를 모두 실행해줘.
```

### 12.2 멤버십과 클라우드 동기화

```text
AGENTS.md를 기본 프로젝트 명세로 읽고,
docs/EXISTING_FEATURE_PROTECTION.md를 기존 기능 보호 규칙으로 읽고,
docs/MEMBERSHIP_CLOUD_SYNC.md를 추가 기능 명세로 읽어 구현해줘.

Free의 현재 로컬 기능과 기존 동작 계약은 동결된 것으로 간주하고,
Premium 기능은 additive change 방식으로 구현해줘.

Google 로그인, Supabase, Stripe Sandbox가 실패해도
기존 로컬 일정·집중·휴식·차단·알림·리포트 기능은 계속 동작해야 해.

기존 동작 변경이 불가피하면 임의로 진행하지 말고 이유와 대안을 먼저 보고해줘.

기존 테스트를 삭제하거나 기대값을 변경하지 말고,
```
