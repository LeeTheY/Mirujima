# 집중 목표 완료 기반 정산 설계

## 1. 목적

집중 시간이 끝난 뒤 사용자가 `100%`, `80%`, `60%`, `실패`를 주관적으로 고르는 현재 방식을 제거한다. 사용자가 계획에 등록한 세부 목표 중 실제로 완료한 목표를 선택하면 서버가 완료 개수에 따라 등급과 포인트를 계산한다.

이 변경으로 다음을 보장한다.

- 계획에 입력한 세부 목표가 canonical server data로 저장된다.
- 세션 시작 시점의 목표가 세션에 고정되어 정산 기준이 바뀌지 않는다.
- 완료한 목표와 미완료 목표가 세션 결과에 모두 남는다.
- 클라이언트가 완료율을 직접 지정하지 못한다.
- 기존 `0%`, `60%`, `80%`, `100%` 포인트 정책은 유지한다.

## 2. 완료 등급 정책

총 목표 수를 `N`, 완료 목표 수를 `C`라고 할 때 서버가 다음 순서로 등급을 결정한다.

```text
C = 0                  → 0% / 실패
C = N                  → 100% / 성공
C × 2 >= N             → 80% / 성공
그 외                  → 60% / 성공
```

정확히 절반을 완료한 경우 80%로 처리한다.

예시:

| 목표 수 | 완료 수 | 결과 |
|---:|---:|---:|
| 1 | 0 | 0% |
| 1 | 1 | 100% |
| 2 | 1 | 80% |
| 3 | 1 | 60% |
| 3 | 2 | 80% |
| 4 | 1 | 60% |
| 4 | 2 | 80% |
| 4 | 4 | 100% |

획득 포인트는 기존처럼 예약한 self deposit에 등급을 곱한 정수 금액이다.

```text
earnedPoints = floor(selfDepositPoints × completionPercent / 100)
returnedPoints = selfDepositPoints - earnedPoints
```

## 3. 데이터 계약

### 3.1 계획 목표

`packages/contracts`의 기존 `FocusPlan`에 `goals`를 additive하게 추가한다.

```ts
export interface FocusGoal {
  id: string;
  name: string;
  detail: string;
  minutes: number;
  priority: "low" | "medium" | "high";
}

export interface FocusPlan {
  // 기존 필드 유지
  goals: FocusGoal[];
}
```

목표 제약은 다음과 같다.

- 목표는 1개 이상이어야 한다.
- 목표 ID는 계획 안에서 중복될 수 없다.
- ID는 비어 있지 않은 1~128자 문자열이다.
- 이름은 공백 제거 후 1~120자다.
- 상세 설명은 최대 1,000자다.
- 목표 시간은 1~720분의 정수다.
- 우선순위는 `low`, `medium`, `high` 중 하나다.
- 목표 수 상한은 100개다.

목표별 시간 합계가 전체 집중 시간을 초과하는 경우는 기존 현실성 경고를 유지하되 저장을 차단하지 않는다. 완료 등급은 목표별 시간 가중치가 아닌 완료 개수를 기준으로 한다.

### 3.2 세션 목표 스냅샷

`start_focus_session()`은 검증된 `cloud_schedules.payload.goals`를 `cloud_focus_sessions.payload.goals`에 그대로 복사한다. 이후 정산은 계획의 최신 목표가 아니라 세션 스냅샷만 사용한다.

이 스냅샷은 다음 문제를 방지한다.

- 세션 시작 뒤 목표를 삭제해 100% 조건을 낮추는 행위
- 목표 이름이나 우선순위 변경으로 기록이 달라지는 문제
- 웹과 Extension의 재동기화 시 목표 목록 불일치

### 3.3 정산 결과

세션의 `payload.result`에는 목표별 결과와 집계를 저장한다.

```ts
interface FocusSettlementResult {
  completedGoalIds: string[];
  goalResults: Array<{
    goalId: string;
    completed: boolean;
  }>;
  completedGoalCount: number;
  totalGoalCount: number;
  completionPercent: 0 | 60 | 80 | 100;
  earnedPoints: number;
  returnedPoints: number;
  settledAt: string;
}
```

`goalResults`에는 세션의 모든 목표가 한 번씩 포함되어 완료·미완료 상태를 모두 보존한다. `cloud_schedules`에는 기존처럼 최종 계획 상태와 `updatedAt`을 반영한다. 정산의 canonical 상세 기록은 `cloud_focus_sessions.payload.result`다.

## 4. 서버 API와 검증

기존 정산 함수의 클라이언트 입력을 완료율에서 완료 목표 ID 배열로 변경한다.

```sql
finish_focus_session(
  p_session_id text,
  p_completed_goal_ids text[],
  p_device_id text
) returns jsonb
```

서버는 transaction 안에서 다음을 수행한다.

1. 인증 사용자와 세션 소유권을 확인한다.
2. 세션 상태와 종료 시각을 확인한다.
3. 세션 목표 스냅샷이 1개 이상인지 확인한다.
4. `p_completed_goal_ids`의 null, 빈 ID, 중복을 거부한다.
5. 전달된 모든 ID가 세션 목표에 존재하는지 확인한다.
6. 완료 개수를 계산하고 등급을 결정한다.
7. 서버가 계산한 등급으로 self deposit을 분할 정산한다.
8. 모든 목표의 완료 여부와 집계를 세션 결과에 저장한다.
9. 계획 상태와 알림·후속 집계가 참조할 최종 상태를 갱신한다.

클라이언트는 `completionPercent`, `earnedPoints`, `returnedPoints`, `totalGoalCount`를 입력하지 않는다.

최초 정산 이후 같은 세션에 다시 요청하면 기존 결과를 반환한다. 두 번째 요청의 완료 목표 목록이 달라도 이미 확정된 금융 원장과 결과는 변경하지 않는다. 기존 advisory lock, row lock, idempotency key를 유지한다.

목표 시간이 끝나기 전에는 완료 목표가 하나 이상인 정산을 거부한다. 기존 조기 포기는 빈 배열을 제출하는 0% 실패 처리로 유지하며 UI에서 확인을 한 번 받는다.

## 5. 웹 UI 흐름

### 5.1 계획 작성

현재 목표 추가·삭제·순서 변경 UI를 유지한다. 계획을 저장할 때 화면의 목표를 `FocusPlan.goals`로 포함한다. 목표 이름이 비어 있거나 시간이 올바르지 않으면 세션을 시작하지 않고 해당 입력 위치에 오류를 안내한다.

### 5.2 집중 종료

타이머가 끝나면 기존 퍼센트 버튼 네 개 대신 세션 목표 체크리스트를 표시한다.

```text
완료한 목표를 선택해 주세요

[✓] 영어 단어 50개 암기
[ ] 수학 문제집 10쪽
[✓] 오답 정리

3개 중 2개 완료 → 80%
예상 획득 800P · 반환 200P

[선택한 목표로 완료 처리]
```

완료 목표를 하나도 선택하지 않으면 다음처럼 명확히 표시한다.

```text
완료 목표 없음 → 실패 처리
[완료 목표 없이 실패 처리]
```

정산 요청 중에는 중복 제출을 막고, 성공 응답 이후 서버가 반환한 목표 결과·등급·포인트를 표시한다. 실패하면 선택 상태를 보존하고 재시도할 수 있게 한다.

### 5.3 안내 문구

집중 사용법 가이드와 종료 체크리스트 상단에 다음 정책을 안내한다.

```text
포인트는 완료한 목표 개수로 계산됩니다.
전부 완료하면 100%, 절반 이상이면 80%, 1개 이상이지만 절반 미만이면 60%,
완료한 목표가 없으면 실패(0%)로 처리됩니다.
```

정확히 절반도 80%라는 설명을 가이드의 예시에 포함한다.

## 6. 호환성과 마이그레이션

새 테이블을 만들지 않고 기존 `cloud_schedules.payload`와 `cloud_focus_sessions.payload`를 확장한다.

새로 생성하는 계획에는 `goals`가 필수다. 배포 전에 생성된 기존 계획이나 활성 세션에 `goals`가 없을 수 있으므로 다음 호환 정책을 적용한다.

- 아직 시작하지 않은 기존 계획: 웹에서 열 때 단일 목표를 생성하도록 유도하고, 목표가 저장되기 전에는 시작하지 않는다.
- 배포 시점에 이미 활성화된 기존 세션: 기존 `finish_focus_session(text, integer, text)` overload를 유지하되, 서버가 세션 payload에 `goals`가 없음을 확인한 경우에만 정산한다. `goals`가 있는 세션에서 이 overload를 호출하면 `legacy completion is not allowed` 오류로 거부한다.
- 새 목표 기반 세션: 완료율 직접 입력을 절대 허용하지 않는다.

신규 웹 UI는 배열 signature만 호출한다. 레거시 overload는 기존 세션을 정산할 수 있도록 이번 구현에서는 제거하지 않으며, 별도의 정리 작업에서 목표 없는 미정산 세션이 없음을 확인한 뒤 제거한다.

## 7. 오류 처리

사용자 메시지는 원시 DB 오류를 노출하지 않고 다음 행동을 알려준다.

- 종료 시각 전 제출: `목표 시간이 끝난 뒤 완료한 목표를 제출할 수 있습니다.`
- 존재하지 않는 목표: `목표 정보가 변경되었습니다. 세션을 새로 불러온 뒤 다시 시도해 주세요.`
- 중복 제출: 기존 확정 결과를 정상 응답으로 표시한다.
- 네트워크/정산 실패: `선택한 목표는 이 화면에 유지됩니다. 연결을 확인한 뒤 다시 시도해 주세요.`
- 목표 스냅샷 누락: 레거시 호환 대상이 아니면 포인트를 변경하지 않고 운영 확인이 필요한 오류로 처리한다.

## 8. 테스트와 회귀 방지

### 8.1 공유 계약 테스트

- 목표 1개 이상을 포함한 계획을 정상 파싱한다.
- 빈 목표, 중복 ID, 잘못된 시간·우선순위, 100개 초과를 거부한다.
- 기존 도메인 정규화와 계획 필드가 유지된다.

### 8.2 웹 테스트

- 목표 입력이 저장 payload에 포함된다.
- 타이머 종료 전 완료 제출이 비활성화된다.
- 체크한 목표 수에 따라 0/60/80/100 예상 등급이 표시된다.
- 정산 요청에는 완료 목표 ID만 포함된다.
- 실패 후에도 체크 상태가 유지된다.
- 가이드에 산정 정책과 정확히 절반의 예시가 표시된다.

### 8.3 데이터베이스 테스트

- 계획 저장 RPC가 목표 배열을 검증하고 보존한다.
- 세션 시작 RPC가 목표를 스냅샷으로 복사한다.
- 1·2·3·4개 목표의 경계값이 정책대로 계산된다.
- 빈 배열은 0%, 전부 선택은 100%가 된다.
- 중복 ID와 세션에 없는 ID를 거부한다.
- 종료 시각 전 양수 완료를 거부한다.
- 정산 결과에 모든 목표의 완료 여부가 저장된다.
- 60/80/100 포인트 분할과 0% 전액 반환이 정확하다.
- 동일 세션 재호출이 원장 row를 중복 생성하지 않는다.
- 레거시 목표 없는 활성 세션의 정산 호환성이 유지된다.

### 8.4 Extension 회귀 테스트

- 확장 프로그램이 추가된 `goals` 필드를 포함한 계획을 정상 파싱한다.
- 기존 차단 규칙, alarm, 로컬 세션 변환이 영향을 받지 않는다.

## 9. 범위 제외

이번 변경에는 다음을 포함하지 않는다.

- 목표별 시간 가중치 기반 등급
- 목표 완료 증빙 업로드 또는 자동 판정
- 목표별 실시간 서버 mutation
- 목표별 부분 완료율
- 새로운 데이터베이스 테이블

사용자의 완료 선택은 자기 보고 방식이지만, 기존의 임의 퍼센트 선택보다 구체적인 기록을 남기고 서버가 일관된 정책으로 정산하는 것을 이번 변경의 기준으로 삼는다.
